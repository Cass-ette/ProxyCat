# 本地代理故障恢复

## 故障与操作事故的区别

2026-11-10 的本机安装排查中，一次性安装脚本被通过 `launchctl submit` 提交为会反复运行的任务。脚本首次替换应用后，在恢复连接阶段失败；后续运行再次请求应用退出，并在备份目录已存在时失败，形成重复退出。安装日志中累计出现 901 次 `requesting normal application shutdown`，以及替换备份时的 `Directory not empty`。该操作由开发代理执行，不能归因为应用自行崩溃或自行重启。

当时创建的 `com.cassette.proxycat.install-20261110` 和 `com.cassette.proxycat.install-guard-20261110` 已移除。原始安装日志保留在 `/private/tmp/proxycat-install-20261110/progress.log`。这些是本机临时诊断文件，不随产品分发。首次恢复普通内核失败的具体原因、某次 SIGTERM 的发送者仍未查实。

准备本机验收包时，还核实并移除了诊断期间留下的 `io.proxycat.submit`：其命令为一次性的 `proxyctl guard`，移除时处于空闲状态。它不是 TUN 系统助手，也不是正式的独立守护；清理它是为了避免重复执行干扰验收。

后续一次性安装任务不得使用 `launchctl submit`。安装前应具备独立于开发会话的本地恢复手段；完成后必须确认任务已结束且不会重新执行。构建、测试和打包均不应启动、替换运行中的应用或切换其网络配置。

## 产品侧的恢复职责

macOS 的系统代理设置会在应用被强制结束后保留。正常退出仍按“取消进行中的连接操作 → 关闭系统代理 → 停止内核”的顺序清理；`SIGKILL` 或崩溃跳过退出回调时，由独立守护补救。

- 开启系统代理前，先检查 `127.0.0.1:7890`，再确认独立守护的本地握手成功。TUN 开启也不能跳过端口检查；显式指向本地端口的程序仍需要该监听。
- 守护独立于应用进程组，每 5 秒检查一次。普通内核失效时尝试恢复；连续 3 次恢复失败后，仅关闭仍指向 `127.0.0.1:7890` 的系统代理条目。系统调用和启动等待也需要时间，这不是精确的恢复时限。
- 守护与启动、停止、重启及 TUN 切换共用跨进程锁。正在切换时跳过本轮，也不增加失败计数；TUN 活跃时不另起普通内核。显式停止内核先关闭系统代理和守护，内部重启期间保留守护。
- 守护使用内核文件锁保证单实例，本地 Unix 套接字提供就绪和停止请求。套接字目录只允许当前用户访问；不依赖 PID 文件判断身份，也不按残留 PID 向进程发送终止信号。
- 自动清理前逐项重读各网络服务的 HTTP、HTTPS、SOCKS 设置；其他地址或端口不属于该守护的处理范围。手动“关闭系统代理”保留原有关闭全部系统代理的行为。

本地监听可用只说明代理入口可连接，不能证明节点或网站可达。清除失效的系统代理能恢复直接连接的机会，不能保证原本就无法直连的网站可用。独立守护也不能保证自身被强制结束或注销后继续运行。

## 不改动本机网络的验证

### TUN 关闭后的监听恢复

2026-11-10 的本机验收发现另一条独立故障：关闭 TUN 后，日志出现 7890/9090 绑定失败；随后普通内核进程仍在、控制接口可用，但控制配置中的 `mixed-port` 为 0，7890 无监听。仅检查进程会让后续启动一直复用该失效状态。端口占用日志本身不能确认具体的信号发送者、占用者或竞态来源，也不能据此认定 SIGKILL 必然导致绑定失败。

启动和守护现在共同验证普通内核的监听与控制配置。确认归属后先尝试仅重新绑定 mixed 端口，失败后重新检查归属、正常停止旧进程并等待退出，再启动和验证新进程。TUN 会话不在此路径中被替换；仍无法恢复时继续保留关闭失效系统代理的保护。TUN 停止得到成功回复后，也继续核实内核是否仍在退出，避免把收到回复当作资源已释放。

真实内核测试使用随机端口复现 TCP 占用后的 `mixed-port: 0`，验证解除占用后原进程恢复监听；另验证无法通过控制器恢复时的进程替换、SIGKILL 后守护启动新内核且不触发模拟代理关闭。所有系统代理状态及修改仍为测试替身，不改变本机配置。

```bash
cd helper
go test -race ./internal/guard ./internal/sysproxy ./internal/core ./cmd/proxyctl
go test ./...
cd ..
bash scripts/test-shutdown.sh
```

决策测试替换系统代理、内核和 TUN 查询。命令行测试使用临时 HOME、模拟 `networksetup` / `scutil` / `pgrep`；父进程强制退出测试使用自己的子进程、独立进程组和模拟心跳，不结束真实应用或内核。测试还覆盖过期 PID、重复守护、残留套接字、就绪失败以及只清理所属代理条目。

源码与编译检查不等于已安装。真实网络切换验收遵循 [TUN 切换验证](tun-testing.md)，不得把正在依赖该代理的开发会话作为唯一恢复入口。

### TUN 关闭后的端口交接与过期结果

较早一轮验收中，21:00:40 日志记录 TUN 退出，随后两次普通内核启动都在 7890/9090 绑定时报 `address already in use`，最终控制接口不可用。该轮关闭时系统代理原本就关闭，因此不能把现象归因于残留的系统代理。后来做端口级实测才定位到 7890 的跨用户端口状态问题。

在确认真实根因前，普通内核恢复曾先等待代理端口和控制端口重新绑定，最多 45 秒。该防护避免启动一个端口没有监听的内核，但无法消除 macOS 对 root 与用户 socket 状态的等待。

另一个已用模拟 helper 复现的界面缺陷是：TUN 命令和状态确认完成后，慢节点刷新仍持有“正在切换”标志。现在确认结束即释放开关，关闭提示明确说明正在恢复普通代理，不再显示首次授权提示。

最新两轮真实 TUN 切换复现了约 31 秒和约 1 秒的关闭时长。慢轮次停止和端口释放都不到 0.4 秒，额外时间发生在普通内核恢复阶段。逐端口绑定探测确认只有 7890 仍返回 `Address already in use`，9090 已可绑定。结合 Apple XNU 按 socket 所属 UID 判定本地端口冲突的实现，根因是 root 权限 TUN 内核关闭连接后留下的本地端口状态，暂时挡住普通用户内核重用 7890。

修复让固定的 7890 代理入口和 9090 控制入口由普通用户权限的本地 relay 持有；TUN 内核改用会话私有的高位端口。控制 API 仍走同一认证令牌，`/configs` 对外继续报告 7890，监听恢复补丁则映射到内部端口；TCP/UDP 代理流量仍转发，连接记录会把 relay 连接还原成原始本地应用端点。TUN 关闭先停止 relay 和特权内核，普通内核再立即接管固定入口，不再等待管理员 socket 状态超时。助手保留协议 2 并用能力标记识别新 relay，旧版 App 不会把新助手误判为版本不匹配；首次使用新版本仍需授权更新系统助手一次。端口冲突、认证、配置映射、TCP/UDP 转发、活跃连接清理和端口立即重绑均有隔离测试。

`tun on/off --json` 以 NDJSON 报告实际阶段，包含准备、授权（仅安装/更新）、停止、释放端口、恢复或验证。界面依据实际事件显示当前阶段，并独立计时和持续动画，不使用估计百分比。隔离测试验证命令未结束时进度就已到达，结束后清理动画与计时状态。最新的本机切换计时及恢复检查记录在 `dist/tun-port-diagnosis-20261111` 对应报告中。

诊断和连接测试仅代表检测时的网络状态。主动切换 TUN、系统代理、模式、节点、配置及内核，或轮询发现内核、代理、Wi-Fi、节点选择及状态读取可用性改变时，将旧诊断降为历史记录。报告和检测时间继续保留，界面提示“上次结果仅供回看”，旧结论、检查标签改为“上次”，停用过期修复入口，当前错误仍优先展示。内核持续未启动、控制器连续不可读不算每轮发生新变化，已诊断的故障报告和恢复按钮不会被 5 秒轮询清掉。重新诊断失败或异步完成时网络已经改变，保留上次/返回的报告作为历史，不能清除新的失败信息；未变化的刷新保留有效结果。用户可主动“清除记录”；复检进行中禁止清除或重复修复。该逻辑使用模拟 helper 验证，不操作本机网络。

## 诊断与修复入口（#10）

诊断现在区分“本地文件”“运行状态”“联网测试”，显示检测时间。文件存在只说明存储项存在；内核进程存在、控制器返回配置、7890 接受 TCP 连接、通过该代理取得测试地址预期的 HTTPS 204 响应是不同的证据。控制器失联或端口未就绪时，联网测试标记为“未检查”，不能显示“全部通过”。测试通过也只代表 `https://www.gstatic.com/generate_204` 在检测时可达，不证明所有应用已接管。TUN 接口已启用而系统代理关闭是有效组合；接口未就绪或 TUN 交接未确认时另行提示。

诊断只读，不自动启停或切换网络。普通链路未就绪时，明确的“恢复本地代理并复检”按钮复用 `core start` 的 `EnsureProxyReady` 和生命周期锁；存在 TUN 会话时不提供该普通内核替换操作。用户主动选择“开启系统代理并复检”才会开启接管；检测具体网站则复用已有网站检查窗口，涉及全局模式的确认和恢复仍在该窗口处理。操作后重新诊断，命令失败仍保留，不能用一次命令成功遮盖端口或 HTTPS 失败。诊断整体最多等待约 15 秒，实际 HTTPS 访问最多 8 秒，不跟随重定向或跳过证书验证。

隔离回归覆盖进程存活但监听缺失、控制器失联/认证失败/无效响应、其他监听占用、系统代理关闭/部分启用/其他地址、TUN 开启但系统代理关闭、TUN 接口未就绪、HTTPS 超时/证书错误/非预期 HTTP 响应及取消。Swift 假 helper 回归还覆盖操作后复检、命令成功但故障仍在、错误保留、TUN/校园网保护、重复点击和状态变化作废。测试不改变开发机的 TUN 或系统代理。


## 订阅与网站偏好的配置应用

订阅更新和网站偏好共用生命周期锁及配置事务。普通内核应用前确认进程属于 ProxyCat，保存当前模式和手选节点，再向现有控制接口提交经过 Mihomo 校验的配置。返回成功后还要确认控制接口、7890 和仍有效的节点选择。应用失败时尝试重新应用旧配置并验证；磁盘上的活动配置、原订阅基础、配置副本和偏好一起回退。若旧配置的运行状态无法确认，明确报错，并将应用记录降为“未确认”，不能保留此前“已应用”的成功提示；恢复确认后才显示“已回退”。后台更新不改变系统代理开关。

存在 TUN 会话标记或控制器报告 TUN 启用时，不执行这条普通配置应用路径，也不自动关闭或重启 TUN；新配置保存在磁盘，提示下次正常关闭或重开 TUN 时应用。界面分别呈现订阅下载/保存状态和配置应用状态；普通核心真正新启动或 TUN 成功交接后才更新应用记录，后续配置内容改变会撤下旧应用结论。GeoIP 更新状态展示仍暂缓。

普通模式的网站偏好应用后，实际请求同一网站（检测窗口保留原 URL、协议和端口；连接记录默认请求该域名的 HTTPS 首页）。仅规则模式、选定域名/精确 IP 规则和实际节点链同时吻合，才确认偏好命中；MATCH 恰好走同一路径不算验证成功。网站超时、证书或 HTTP 错误独立报告，偏好命中不等于网站可用。TUN 待生效、引擎关闭、非规则模式和应用失败时不拿旧规则复测后声称生效。移除偏好后重新请求并显示订阅当前路径；网络/模式/配置变化使旧请求证据失效。

测试使用假控制接口、临时 HOME 和模拟 helper；可用 `PROXYCAT_TEST_MIHOMO=/path/to/mihomo go test ./internal/controller -run TestReloadConfigWithIsolatedMihomo -count=1 -v` 在 helper 目录额外检查真实内核。此测试将引擎复制为独立名称，用随机回环端口和私有数据目录运行，不修改系统代理、DNS 或路由，不使用 7890/9090，退出时清理测试进程。
